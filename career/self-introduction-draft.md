# 자기소개서 문항 초안

**용도** 게임 클라이언트 개발 지원용 / 공개 가능한 경험 중심  
**작성 원칙** 확인된 작업과 배운 점만 사용하며, 특정 기업의 지원 동기는 임의로 작성하지 않습니다.

## 01. 직무와 관련된 경험

C++과 Unreal Engine을 공부하면서 기능을 직접 구현하고, 동작이 예상과 다를 때 원인을 찾아 수정하는 경험을 쌓았습니다.

Unreal Engine 팀 프로젝트 Project Priest에서는 적 AI와 무기 파츠 작업을 맡았습니다. Behavior Tree와 Blackboard를 사용해 순찰, 감지, 추적, 공격을 연결했지만, 각 행동을 개별적으로 작동시키는 것보다 전환 조건을 자연스럽게 맞추는 작업이 더 어려웠습니다. 플레이어를 놓쳤을 때 어떤 값을 유지하고 언제 순찰로 돌아갈지 검토하면서 실행 흐름과 Blackboard 상태를 함께 확인했습니다.

최근 Don't Drop에서는 캐릭터 이동과 입력을 맡아 DataTable 설정을 CharacterMovementComponent에 적용하고, 방어구 무게가 바뀌면 이동 속도를 다시 계산하는 흐름을 연결했습니다. 프로젝트마다 다루는 기능은 다르지만, 실제 동작과 데이터 전달 경로를 확인하는 경험을 이어 가고 있습니다.

## 02. 문제 해결 경험

Project Priest에서 공격 애니메이션은 재생되는데 적의 공격 피해가 적용되지 않는 문제가 있었습니다. 단순히 공격 범위가 존재하는지만 확인하기보다 Overlap 이벤트, 저장한 대상, Notify에서 피해를 적용하는 시점을 나눠 살펴봤습니다. 충돌 Box 높이를 바꾸자 일부 상황에서 판정이 더 안정적인 현상을 관찰했고, 팀 발표 자료에는 Notify 시점의 직접 범위 검사 접근도 남겼습니다.

문제가 발생했을 때 어느 함수에서 끊겼는지, 어떤 조건에서 실행되는지 확인해야 한다는 점을 배웠습니다. 다만 최종 제출 코드가 각 시도의 어떤 형태였는지는 다시 대조해야 합니다.

## 03. 협업 경험

무기 파츠와 UI는 서로 다른 담당자가 작업했습니다. 장착한 파츠가 능력치에 영향을 주고 화면에도 표시되어야 했으므로 데이터가 어디에 저장되고 어떤 형태로 넘어가는지 함께 확인했습니다.

Don't Drop에서는 전투·방어구 상태를 담당하는 팀원의 기능을 캐릭터 이동·입력에 연결했습니다. 이동 코드만 독립적으로 작성하기보다 방어구 무게 변경과 전투 요청이 전달되는 지점을 먼저 맞췄습니다.

팀 TextRPG에서는 Git 브랜치·PR·병합과 충돌 해결을 경험했습니다. 당시 회고에는 기능 범위와 작업 경계를 더 일찍 맞추면 통합 과정이 수월했을 것이라는 내용도 남아 있습니다.

## 04. 학습과 개선 방식

기능 구현 과정에서 이해되지 않는 부분이 있으면 역할과 실행 위치를 나눠 정리합니다. ChatX에서는 GameMode와 PlayerController의 역할, Server·Client RPC와 Replication의 차이를 실제 숫자 야구·채팅 코드를 작성하면서 확인했습니다.

모르는 개념을 사용 경험처럼 포장하기보다, 어떤 부분까지 구현·검증했고 어디부터 추가 확인이 필요한지를 설명하려고 합니다.

## 제출 전 확인

기업 지원 동기, 글자 수, 지원 직무의 필수 기술을 확인해 문항별로 다시 편집해야 합니다. 특정 기업의 문화·제품 경험, 정량적 성과, 학력·경력은 이 공개 초안에서 임의로 추가하지 않았습니다.
