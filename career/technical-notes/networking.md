# Unreal 멀티플레이 기술 노트

> ChatX 숫자 야구 및 Don't Drop 관련 학습·설계 기록을 바탕으로 한 개념 정리입니다. 모든 네트워크 환경에서의 동작 검증을 의미하지 않습니다.

## Authority와 로컬 조작

- `HasAuthority()`: 현재 실행 환경이 해당 Actor에 대한 Authority를 가지는지 확인
- `IsLocallyControlled()`: Pawn/Character가 현재 실행 환경의 로컬 Controller에 의해 조작되는지 확인
- 리슨 서버 호스트는 서버이면서 로컬 플레이어이기도 하므로 두 조건을 같은 뜻으로 취급하면 안 됩니다.

## RPC의 종류

| 구분 | 주로 실행되는 곳 | 대표 용도 |
| --- | --- | --- |
| Server RPC | 서버 | 소유 클라이언트의 서버 작업 요청 |
| Client RPC | 해당 Actor의 소유 클라이언트 | 소유자에게 결과·UI 이벤트 전달 |
| NetMulticast RPC | 서버 및 관련 복제 클라이언트 | 전체에 알려야 하는 일회성 연출 |

RPC 호출에는 소유권, Actor 복제 상태, 호출 위치 같은 조건이 영향을 줍니다. Multicast만으로 지속적인 상태 동기화가 자동 보장되는 것은 아닙니다.

## Replication과 RPC

- **Replication:** 현재 게임 상태를 클라이언트에 동기화하는 데 사용
- **RPC:** 특정 실행 환경에서 동작을 요청하거나 이벤트를 전달하는 데 사용
- 실제 설계에서는 서버가 신뢰할 상태와 클라이언트의 화면 전용 처리를 분리합니다.

## 숫자 야구 예시 흐름

1. 소유 클라이언트가 입력을 받습니다.
2. 서버에 입력 또는 게임 동작을 요청합니다.
3. 서버에서 규칙에 따라 입력을 검증합니다.
4. 결과를 필요한 클라이언트 또는 참가자에게 전달합니다.

위 흐름은 학습 내용을 설명하기 위한 예시입니다. 실제 구현의 모든 RPC 이름·인수·호출 순서는 소스코드와 대조해야 합니다.

## 리슨 서버 테스트 점검

- 호스트와 원격 클라이언트에서 동일한 동작이 보이는가?
- `HasAuthority()` / `IsLocallyControlled()` 결과가 예상과 일치하는가?
- RPC를 요청한 객체에 올바른 Owner가 설정되어 있는가?
- 서버에서 생성·변경한 Actor가 다른 클라이언트에도 나타나는가?
- 이동, 공격, 사망, 관전 같은 상태 전환이 각 클라이언트에서 일관되는가?
- PIE와 별도 PC·온라인 세션 테스트 결과를 구분했는가?
