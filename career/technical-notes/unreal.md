# Unreal Engine 기술 노트 — 게임플레이 구조

> Unreal Engine 5 학습과 Project Priest·Don't Drop 작업 기록을 토대로 한 정리입니다. 설명용 구조와 실제 최종 구현을 구분합니다.

## 주요 클래스의 역할

| 클래스 | 대표 역할 | 네트워크 관점 |
| --- | --- | --- |
| GameMode | 게임 규칙·진행과 플레이어 입장 처리 | 서버에 존재 |
| GameState | 참가자에게 공유할 게임 전체 상태 | 서버에서 복제 가능 |
| PlayerState | 플레이어별 공유 상태 | 서버에서 복제 가능 |
| PlayerController | 플레이어 입력·조작과 소유 클라이언트 통신 | 서버와 해당 소유 클라이언트 |
| Character / Pawn | 플레이어 또는 AI가 조작할 수 있는 액터 | 역할과 설정에 따라 복제 |
| ActorComponent | 액터의 기능을 분리·조합 | 컴포넌트별 복제 조건 확인 |

## 캐릭터 이동과 카메라

- **Enhanced Input:** 입력 액션과 매핑 컨텍스트를 통해 입력 처리
- **CharacterMovementComponent:** 속도·가속·감속·점프·공중 제어 등 이동 동작의 기반
- **카메라:** 로컬 입력으로 시점을 조작하는 부분과 서버에 공유할 상태를 구분
- **전투 연동:** 방어·넉백·장비 무게 같은 상태가 이동을 제한할 경우 책임 경계와 데이터 전달 경로를 정리

Don't Drop의 캐릭터·조작 설계에서 검토한 항목이며, 실제 최종 적용 여부는 소스 확인이 필요합니다.

## AI 구성 — Project Priest

1. 감지 또는 상태 갱신으로 Blackboard 값을 설정합니다.
2. Behavior Tree의 Decorator가 조건을 판단합니다.
3. Task가 이동·대기·공격 같은 동작을 실행합니다.
4. 대상이 사라지거나 조건이 달라지면 다음 행동으로 전환합니다.

Project Priest에서는 순찰·감지·추적·공격의 연결과 조건 점검이 주요 작업이었습니다.

## 데이터와 Blueprint 연동

DataTable은 데이터 행을 정의해 코드와 설정 값을 분리할 때 유용합니다. Blueprint와 C++가 함께 쓰이는 프로젝트에서는 실제 Mesh, 컴포넌트, 이벤트 호출 대상이 무엇인지 확인해야 합니다. Project Priest의 사망 처리에서는 C++의 GetMesh()와 실제 보이는 Blueprint Mesh가 달랐던 문제가 기록되어 있습니다.

## 구현 검증 시 확인

- 입력은 어느 환경에서 처리되는가?
- 서버 권한이 필요한 상태 변경은 무엇인가?
- Replication 대상과 로컬 전용 값이 섞이지 않았는가?
- 애니메이션 Notify의 실행 시점과 실제 공격 판정이 일치하는가?
- 데이터 행과 Blueprint 설정이 실제 사용하는 인스턴스를 가리키는가?
